## 1. Core Concepts

```hcl
# provider — which API Terraform talks to
provider "aws" {
  region = "us-east-1"
}

# resource — something Terraform creates/manages/destroys
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

# data source — read-only lookup of something that already exists
data "aws_availability_zones" "available" {
  state = "available"
}

# variable — input parameter
variable "cluster_name" {
  type    = string
  default = "mastery-cluster"
}

# output — value exposed for other configs/modules or CLI inspection
output "vpc_id" {
  value = aws_vpc.main.id
}
```

- **Resources** are the only blocks with a real-world side effect (create/update/destroy).
- **Data sources** never modify anything — they just read existing state (e.g., an
  existing AMI ID, an existing Route53 zone) to reference in resources.

## 2. State — The Most Important Concept to Get Right

- `terraform.tfstate` is Terraform's record of what it believes exists in the real
  world, mapped to your configuration. Every `plan`/`apply` diffs **configuration
  vs state vs real infrastructure**.
- **Local state is a single point of failure and a collaboration blocker** — only
  acceptable for solo learning labs.
- **Remote state** (S3 + DynamoDB lock, Terraform Cloud, Azure Storage + blob lease)
  is required for any team/production use:
  - Enables **locking** — prevents two people from running `apply` simultaneously
    and corrupting state.
  - Enables **shared visibility** — anyone on the team can `terraform plan` against
    the current real state.

```hcl
terraform {
  backend "s3" {
    bucket         = "my-org-terraform-state"
    key            = "clusters/mastery-cluster/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}
```

**Critical security point:** state files often contain **secrets in plaintext**
(DB passwords generated by a resource, private keys, connection strings) even if
your `.tf` files never hardcode them. Treat the state backend with the same
access controls as a secrets manager — encrypt at rest, restrict IAM access,
never commit `.tfstate` to git.

## 3. The Core Workflow

```bash
terraform init                 # downloads providers/modules, configures backend
terraform validate              # syntax/internal consistency check
terraform plan -out=tfplan       # shows exactly what will change — REVIEW THIS
terraform apply tfplan           # applies exactly the reviewed plan, no surprises
terraform destroy                # tears down everything Terraform manages here
```

**Staff-level discipline:** always `plan` and save it (`-out=tfplan`), review the
diff (additions/changes/**destructions** — pay special attention to anything
showing `-/+` replace), and `apply` that exact saved plan — never `apply` blind
or `apply` a plan that was generated against a now-stale state.

## 4. Modules — Composition Over Duplication

```hcl
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 20.0"      # ALWAYS pin module versions

  cluster_name    = var.cluster_name
  cluster_version = "1.31"
  vpc_id          = module.vpc.vpc_id
  subnet_ids      = module.vpc.private_subnets
}
```

- **Consuming community modules** (like `terraform-aws-modules/*`) is the 80% case
  for most engineers — you rarely need to write a module from scratch for common
  infrastructure (VPC, EKS, RDS all have mature, widely-used modules).
- **Authoring your own modules** matters when you need to standardize a pattern
  across many teams (e.g., "our standard S3 bucket with logging + encryption +
  lifecycle policy enforced") — same motivation as a Helm library chart.
- Always pin module **and** provider versions (`~> 20.0`) — unpinned modules are
  the Terraform equivalent of `:latest` image tags: a silent, un-reviewable
  source of drift.

## 5. Workspaces vs Directory-per-Environment

| Approach | How | Tradeoff |
|----------|-----|----------|
| **Terraform workspaces** | `terraform workspace new staging` — same config, separate state per workspace | Simple, but easy to accidentally apply to the wrong workspace; all environments share identical structure (can't diverge easily) |
| **Directory-per-environment** | `environments/staging/`, `environments/prod/`, each with its own backend config and `.tfvars` | More explicit and safer (you `cd` into the environment you mean to touch), allows environments to diverge structurally, more files to keep in sync |

**Most staff-level teams prefer directory-per-environment** for production
infrastructure — the explicitness (you can't `apply` to prod by forgetting to
switch a workspace) outweighs the extra duplication, and it mirrors how
Kustomize/Helm values-per-environment already works in your Kubernetes tooling.

```
infra/
├── modules/
│   ├── vpc/
│   └── eks-cluster/
├── environments/
│   ├── staging/
│   │   ├── main.tf         # calls the modules
│   │   ├── backend.tf       # staging's own remote state
│   │   └── terraform.tfvars
│   └── production/
│       ├── main.tf
│       ├── backend.tf
│       └── terraform.tfvars
```

## 6. Drift Detection & Import

- **Drift** = someone (or something) changed real infrastructure outside of
  Terraform (console click-ops, another automation tool) — state no longer
  matches reality.
- Detect it with `terraform plan` on a schedule (CI cron) — any unexpected diff
  on a plan with no configuration changes is drift.
- **`terraform import`** brings existing, unmanaged infrastructure under Terraform
  management without recreating it:

```bash
terraform import aws_vpc.main vpc-0123456789abcdef0
# Then write matching `resource "aws_vpc" "main" {...}` config until `plan` shows no diff
```

- **Staff-level practice:** treat drift as an incident-worthy signal, not just an
  annoyance — it usually means someone bypassed the review/approval process that
  Terraform + CI/CD was supposed to enforce.

## 7. Secrets in Terraform

- **Never hardcode secrets** in `.tf` files or `.tfvars` committed to git.
- Reference secrets via data sources at apply time instead:

```hcl
data "aws_secretsmanager_secret_version" "db_password" {
  secret_id = "prod/myapp/db-password"
}

resource "aws_db_instance" "main" {
  password = data.aws_secretsmanager_secret_version.db_password.secret_string
  # ...
}
```

- Remember: even referenced this way, the resolved value **still ends up in
  `terraform.tfstate`** in plaintext — this is exactly why state backend security
  (encryption, restricted IAM access) matters as much as the secrets manager itself.
- For values that must be provided at `plan`/`apply` time locally, use `-var-file`
  with a git-ignored `.tfvars`, or a SOPS-encrypted file decrypted just-in-time in CI.

## 8. CI/CD for Terraform

```yaml
# Conceptual pipeline shape (GitHub Actions / GitLab CI / any CI)
# On Pull Request:
#   terraform init
#   terraform validate
#   terraform plan -out=tfplan    -> post plan output as a PR comment for review
#
# On merge to main (after human approval of the plan):
#   terraform apply tfplan         -> apply the EXACT plan that was reviewed
```

- **Plan on PR, apply on merge** is the standard pattern — this is Terraform's
  equivalent of the GitOps model you already use for Kubernetes manifests (Day 6):
  the diff is reviewed by a human before it takes effect, and the applied change
  is always traceable to a merged commit.
- Add a manual **approval gate** before `apply` for production environments —
  automatic apply-on-merge is reasonable for dev/staging, risky for prod without
  a human sign-off step.

## 9. Terraform vs Kubernetes/Helm — Where the Boundary Sits

```
Terraform   → provisions infrastructure OUTSIDE the cluster's own API
              (VPC, subnets, the EKS cluster resource itself, IAM roles,
               RDS, S3, DNS records, node groups)
                        │
                        ▼
Kubernetes  → orchestrates workloads INSIDE the cluster
              (Pods, Deployments, Services — objects the K8s API server owns)
                        │
                        ▼
Helm        → packages/templates the Kubernetes objects above for repeatable deploys
```

- **Rule of thumb:** if it's a resource the Kubernetes API server doesn't know
  about (the cluster itself, a VPC, an IAM role, a managed database), it belongs
  in Terraform. If it's an object the K8s API server manages (Deployment,
  Service, ConfigMap), it belongs in Helm/Kustomize/GitOps — **don't manage
  Kubernetes objects with the Terraform Kubernetes/Helm providers** in most cases;
  it creates two competing sources of truth (Terraform state vs. cluster reality)
  for the same objects, and loses you `kubectl diff`/GitOps drift-correction.
- The one common exception: using Terraform to create the **ServiceAccount +
  IAM role trust** for IRSA (Section 12 in Day 14) — that's genuinely an
  infrastructure-identity concern that spans both AWS IAM and the cluster's OIDC
  provider, so it's reasonable for Terraform to own that narrow seam.

## 10. Hands-On Lab

```bash
mkdir terraform-lab && cd terraform-lab

cat > main.tf <<'EOF'
terraform {
  required_providers {
    random = { source = "hashicorp/random" }
  }
}

resource "random_pet" "demo" {
  length = 2
}

output "pet_name" {
  value = random_pet.demo.id
}
EOF

terraform init
terraform plan -out=tfplan
terraform apply tfplan
terraform show                 # inspect current state
terraform state list            # list resources tracked in state
terraform destroy
```

Follow with the real exercise: provision the EKS cluster from
[day-14-eks/README.md](../day-14-eks/README.md) Section 12 using the AWS provider
and the `terraform-aws-modules/eks/aws` module.

## 11. Interview Points (Staff-Level)
- "State is the single source of truth Terraform reasons from — I always use a
  remote backend with locking for anything beyond a personal lab, and I treat
  the state backend's access controls as seriously as a secrets manager, because
  state routinely contains plaintext secrets."
- "I never `apply` without reviewing a saved `plan` first — especially watching
  for `-/+` (destroy and recreate) on anything stateful."
- "I draw a hard line between Terraform and Kubernetes tooling: Terraform owns
  infrastructure the K8s API server doesn't know about (the cluster, VPC, IAM);
  Helm/GitOps owns objects inside the cluster. I avoid using Terraform's
  Kubernetes/Helm providers to manage in-cluster objects — it creates two
  competing sources of truth for the same resources."
- "Drift is a process signal, not just a technical one — if `plan` shows
  unexpected changes with no corresponding merged commit, someone bypassed
  review, and that's worth investigating like an incident."
- "For environment separation I prefer directory-per-environment over Terraform
  workspaces in production — it's more explicit about what you're about to
  change, at the cost of some duplication."
